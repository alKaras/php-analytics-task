## Part A - Sql Optimization

### Що не так з легасі схемою

- `created_at` зберігається як varchar - для пошуку в діапазоні потрібно використовувати CAST() для кожного рядку,
  що унеможливлює використання індексу і приводить до повного скану таблиці
- `id` зберігається як INT - небезпечно, якщо к-сть рядків в таблиці буде дуже великий
- `country` як VARCHAR(3) - за стандартом ISO 3166-1 правильніше використовувати тільки 2 символа для позначення країни
- `device` як VARCHAR(16) - без валідації, будь-яке значення приймається
- Відсутність індексів - кожен запит сканує таблицю

### Що було покращено

- `created_at` - DATETIME NOT NULL - зберігає значення як є, дозволяє range scan по індексу
- `id` - BIGINT UNSIGNED - безпечно для сотень мільйонів рядків
- `url` - VARCHAR(128) - покриває більшість URL сторінок (з параметрами або з довгими slug)
- `country` - CHAR(2) - фіксована довжина, ефективніше зберігання, згідно ISO 3166-1, але якщо потрібно зберігати окремо
  3 значні коди країн, то можна додати окрему колонку `country_iso3166_alpha_3`
- `device` - VARCHAR(16) з COMMENT - валідація делегована додатку через
  enum на рівні коду. Обрав VARCHAR замість енаму через те, що додавання
  нового типу пристрою потребувало б ALTER TABLE, який лочить таблицю на великих даних
- `user_id` - INT UNSIGNED NULL - nullable для підтримки анонімних переглядів
- `url`, `country`, `device` → `NOT NULL` - у легасі схемі всі колонки були
  nullable, що дозволяло вставляти записи без обов'язкових даних. Для аналітики url або країна важливі,
  тому використано NOT NULL щоб валідація була на рівні БД, а не тільки на рівні додатку
- Додано композитний індекс (created_at, country) - покриває фільтр за датою створення і країною
- Додано idx_url (url) - повний індекс оскільки колонка тепер VARCHAR(128),
- Додано idx_user_id - для запитів по користувачу

### Компроміси

- url залишено денормалізованим. Винесення в окрему таблицю `pages` зменшило б дублювання,
  але додало б `JOIN` до кожного запиту. Для OLAP навантаження (багато читань)
  вартість `JOIN` перевищує вигоду від економії місця. Нормалізація була б
  доцільною якби URL потрібно було оновлювати або категоризувати (якщо потрібно знати додатково query параметри, які є у
  url для подальшого фільтрування за ними, то краще винести в окрему таблицю і джойнити за page_id)
- VARCHAR замість ENUM для device - enum виключає можливість безболісно додати новий тип девайсу, ALTER TABLE дорогий
  на великих данних

### A1. Топ-5 сторінок за унікальними користувачами

```sql
-- ДО: повне сканування таблиці, CAST на кожному рядку для валідації значення дати в комірці, повільно на великій вибірці данних
SELECT url, COUNT(DISTINCT user_id) AS unique_users
FROM pv
WHERE CAST(created_at AS DATETIME) BETWEEN '2025-09-15' AND '2025-09-17'
  AND country = 'UA'
GROUP BY url
ORDER BY unique_users DESC LIMIT 5;

-- ПІСЛЯ: range scan по індексу, без CAST
SELECT url, COUNT(DISTINCT user_id) AS unique_users
FROM page_views
WHERE created_at BETWEEN '2025-09-15 00:00:00' AND '2025-09-17 23:59:59'
  AND country = 'UA'
GROUP BY url
ORDER BY unique_users DESC LIMIT 5;
```

Композитний індекс `(created_at, country)` дозволяє MySQL використовувати
range scan по `created_at` і фільтрувати по `country` не скануючи решту таблиці.

### A2. Пакетна вставка

```sql
-- ДО: один INSERT на рядок = окремий запис на диск кожного разу
INSERT INTO pv (...)
VALUES (...);
INSERT INTO pv (...)
VALUES (...);

-- ПІСЛЯ: один INSERT + транзакція
START TRANSACTION;
INSERT INTO page_views (user_id, url, country, device, created_at, duration_ms)
VALUES (1, '/home', 'UA', 'desktop', '2025-09-15 10:00:00', 200),
       (2, '/home', 'UA', 'mobile', '2025-09-15 10:01:00', 300),
       (3, '/product/42', 'PL', 'tablet', '2025-09-15 10:02:00', 450);
COMMIT;
```

Один `INSERT ... VALUES (...), (...)` всередині транзакції зводить множинні
записи на диск і оновлення індексів до одного. Для масового імпорту від 10k+
рядків `LOAD DATA INFILE` підходить краще, але потребує привілею `FILE` на сервері,
що свідомо обмежується з міркувань безпеки, дозволяє читати і записувати файли на сервері, що є
потенційним вектором атаки при неправильному налаштуванні прав.

## Частина B - Рефакторинг PHP у ООП

### Що було не так з легасі кодом

- Процедурний стиль, глобальні функції, відсутність структури
- Відсутність валідації - від'ємний `amount` враховувався як оплачений
- Відсутність логування
- Небезпечний запис у файл - без блокування і обробки помилок

### Що було покращено

**Класи:**

- `OrderStatus` enum - замінює захардкоджені рядки `'paid'` / `'pending'`
- `LogLevel` enum - замінює захардкоджені рядки рівнів логування
- `OrderDTO` - типізований об'єкт передачі даних, будується через `fromArray()`
- `ReportResult` - readonly DTO з результатами підрахунку
- `ReportCalculator` - єдина відповідальність: фільтрація і підрахунок
- `ReportRenderer` - єдина відповідальність: виведення в консоль і файл
- `Logger` - файлове логування з рівнем і часовою міткою
- `ReportApp` - оркеструє процес, містить `process()`, `write()`, `summary()`

**Валідація:** враховуються тільки замовлення з `status = paid` І `amount > 0`.
Від'ємні суми (аномалії) пропускаються і логуються як попередження.

**Безпечний запис у файл:** `flock()` через `fopen/fwrite/fclose` з `try/finally`
гарантує що файловий дескриптор завжди закривається навіть якщо `fwrite` кине виняток.

**Застосовані принципи SOLID:**

- **S** - кожен клас має одну відповідальність
- **O** - новий логер або рендерер = новий клас що імплементує інтерфейс, без змін існуючого коду
- **L** - реалізації `LoggerInterface` і `RendererInterface` є взаємозамінними
- **I** - маленькі точні інтерфейси, не один великий контракт
- **D** - частково: `ReportApp` використовує інтерфейси `LoggerInterface`
  і `RendererInterface` як типи, але створює залежності сам у конструкторі
  через обмеження сигнатури з ТЗ `__construct($orders, $file)`.
  В проекті залежності передавати краще ззовні через конструктор або DI-контейнер.
